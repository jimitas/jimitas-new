## 背景・問題認識

配色リファクタリング（Phase 0〜5）を `1ef8f7e` `ce8f9c5` で完了し、push 済み。
ただし「ビルドは通ったが、実際の見た目で本当にトーンが揃っているか？」を確認できていなかった。

オーナーの問いかけ：

## 議論の変遷（重要な転換点）

### Shift 1: 「直接ブラウザを見る機能はない」という確認

最初は「Claude Code 自身がブラウザを開いて見られるのか？」という素朴な期待だったが、
組み込みでブラウザレンダリングを直接見る機能はないことを共有。代わりに以下の選択肢を提示：

- A. Playwright + Bash でスクショ → Claude が画像を Read で確認
- B. Playwright MCP サーバーを設定して対話的にブラウザ操作
- C. WebFetch で HTML を取って class 検証
- D. CronCreate で定期巡回

### Shift 2: A 案を選択

オーナーは A（Playwright スクショ + 画像 Read）を選択。
理由（推測）：
- B は MCP 設定が必要で導入コストが高い
- C は「レンダリング後の見た目」が分からないので目的に合わない
- D は今回のような単発リファクタリング検証には大げさ
- A は **画像という普遍的な成果物が残る** → ベースライン保存にもなる

### Shift 3: 「画像を Read するだけ」が想像以上に強力だった

実際にやってみると、grep だけでは見つけられなかった raw color の取りこぼしが
**6 箇所**見つかった。これは決定的な発見だった。

## 設計判断のポイント

### 採った選択肢: Playwright + tsx + Read による Claude 視覚確認

```
[npm run dev] → [npm run screenshot] → [PNG 生成] → [Claude が Read で目視]
```

- **依存追加**: `@playwright/test` `tsx` を devDependencies へ
- **ブラウザ**: Chromium のみインストール（Firefox/WebKit は不要）
- **スクリプト**: `scripts/screenshot-all.ts`
  - `apps.ts` から自動でルート一覧を取得（追加コスト 0）
  - viewport 1024×768（プロジェクトのタブレットファースト方針）
  - reducedMotion / locale / timezoneId を固定（再現性のため）
  - 失敗してもスキップして続行
- **出力先**: `screenshots/<YYYY-MM-DD>/` （`.gitignore` 済み）

### 却下した選択肢

| 選択肢 | 却下理由 |
|---|---|
| Playwright MCP | 導入コスト高、まずは A で十分 |
| WebFetch | レンダリング後の見た目が見えない、トーン検証には不向き |
| CronCreate での定期巡回 | 単発検証には大げさ、必要になったら追加 |
| `fullPage: true` | 縦に長いアプリで画像が巨大になり Read コストが上がる |

### トレードオフ

- ❌ 画像は `screenshots/` に大量生成される（54 枚 × 各 100KB〜500KB）
  → `.gitignore` で対応
- ❌ Read で読み込むと context window を消費する
  → 「主要アプリのみ抜粋」で運用、全 54 枚は不要
- ❌ dev server が立ち上がっている前提
  → スクリプト冒頭の説明で明記、ユーザーが既存 dev server を使えるように

## ふりかえり・気づき

### 良かったこと

1. **「Claude Code がマルチモーダル LLM である」という事実をフル活用できた**
   - ChatGPT 等のテキストベース LLM だとこのワークフローは成立しない
   - Read ツールで PNG を読み込むだけで視覚解釈ができる、という基本機能の組み合わせで完結

2. **grep では見つけられない「トーンの浮き」を画像で発見**
   - 例: `bg-green-500`（スタート）は色名でも形式でも問題なく見えるが、
     画像で見るとロゴの brand-400 と比べて鮮やかすぎることが分かる
   - 「ルールに従っているか」より「**意図に従っているか**」を検証できる

3. **スクリプトの再利用性が高い**
   - `apps.ts` を見るだけで全ルートが取得できる設計のおかげで、
     新アプリを追加しても自動で対象になる
   - 「ベースライン保存 → 変更後再撮影 → 差分確認」のループが構築できた

### 反省点・教訓

1. **配色リファクタリングの初動 grep が甘かった**
   - 私は最初 `bg-(red|blue|purple|...)` だけを対象にし、`green` `gray` は除外した
   - 「典型パターン」をスコープとしただけで、「**ボタン色全般**」をスコープにすべきだった
   - 教訓: リファクタリングの「除外条件」を明示的に書く。曖昧だと取りこぼす

2. **「ビルドが通る = 完成」ではない**
   - 型エラーがなくても、視覚的な一貫性は別軸で検証が必要
   - 今後は **「ビルド成功 + 画像目視」をセットで完成判定**

3. **検証コストを下げる仕組みを最初に作るべきだった**
   - 配色リファクタリングのほぼ最後でこのスクリプトを作ったが、
     最初に作っていれば各 Phase 終了時にすぐ目視確認できた
   - 教訓: 大規模リファクタリング前に **「検証ハーネス」を先に整備**

### 想定外だったこと

- スクショ取得が予想以上に速かった（54 ページで数十秒）
- Playwright のブラウザバイナリインストールが Windows でも問題なく動いた
- dev server の状態（既に PID 62228 で動いていた）に救われた
