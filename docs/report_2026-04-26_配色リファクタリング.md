## 背景・問題認識

過去の方針として「ボタン配色は brand / accent / warm トークンを使い、生の Tailwind カラー（red-500 / blue-500 等）は禁止」というルールはあったが、**運用が崩れていた**：

1. **共通ボタン部品（柔らか系）と、最近移植したアプリのインライン書き（強い系）が併存**
   - 旧 BtnQuestion 系: 白背景＋色枠＋ホバーで色変化
   - 最近のアプリ（eawase / nandemo / fushi-dukuri / 筆算系）: 単色背景＋白文字
   - これが「ちぐはぐ感」「最近移植したアプリのボタンが現職っぽい・原色っぽい」の正体だった

2. **リセットボタンの色がアプリ間で全然揃っていなかった**
   - okane: グレー / 筆算系: グレー / eawase・nandemo: warm（オレンジ）/ fushi-dukuri: グレー＋赤ホバー
   - 共通部品 BtnUndo は brand（緑）だったが実際の使用例と乖離
   - 「初期方針 = brand 緑」という私の主張は早合点で、**初期方針自体が一貫していなかった**

3. **ぶろっくのモード切替が raw blue / raw purple のまま**
   - BtnMode 共通部品があるのに使われていなかった（実使用は kuku-yomi の 1 アプリのみ）

4. **トップページのトーンとアプリ内のトーンの乖離**
   - トップページ: brand-400 中心の柔らかいパステル
   - 一部アプリ内: brand-500/600 単色背景の強いトーン

## 議論の変遷（オーナーとの対話で見つかった芯）

最初は「リセットの色をどうするか」で始まったが、議論の中で **本質的な論点が3回シフト** した。

### Shift 1: 「初期方針はどうだった？」
- docs/ を全件調査 → **配色方針の明文化はゼロ**だった
- 唯一の根拠は globals.css の `@theme` コメント（UD配慮の意図のみ）
- メモリには事後の整理しかなかった

### Shift 2: 「カードの緑とボタンの緑は同じにすべきか？」
- 表面的な「リセット色をどうするか」から「**全体のトーン統一**」へ論点が深化
- カード左端=`brand-400`、セクション下線=`brand-400`、トップページの基調が判明
- 「ボタンも同じトーンに揃える」という骨格が定まる

### Shift 3: 「『ブランド』の意味」を再定義
- オーナーの言葉：
  > ブランドといいたいのは、緑だけでなく、オレンジ系・青系・赤系・グレー系などもトーンは統一したいという感じ
- これが **decisive moment**。私が誤解していた「ブランド=brand トークン1色に集約」を撤回し、
  「**ブランド=ロゴと同じ柔らかいトーンで全色を揃える**」という本意を理解
- これにより「-400 ベース白抜き」という新標準が確定した

## 設計判断のポイント

### 1. 「-400 ベース白抜き」を新標準に

```tsx
className="bg-brand-400 hover:bg-brand-500 active:bg-brand-600
           text-white border-2 border-brand-400
           active:translate-y-0.5 transition-colors
           rounded-lg shadow-sm"
```

- 旧「強い系」（-500 単色）→ -400 にひとつ下げた → ロゴと同じトーン
- 旧「柔らか系」（白背景＋色枠）→ 廃止（visual consistency のため）
- ホバー -500、アクティブ -600 の3段グラデーションでフィードバック

### 2. `danger` トークンを新設（rose の値エイリアス）

```css
@theme {
  /* 現状は rose と同値。後で値だけ変えれば全アプリのリセット色が一括変更可能 */
  --color-danger-400: #fb7185;
  --color-danger-500: #f43f5e;
  --color-danger-600: #e11d48;
  /* ... */
}
```

- リセット・停止 = `bg-danger-400` で統一
- **意味的トークン名**（用途を表す名前）と **値**（rose と同値）を分離
- オーナーの「あとで赤からオレンジに戻したいかも」という発言から、**変数化**の必要性が確定 → 1 箇所書き換えで全部変わる設計に

### 3. 「物の色」と「ボタンの色」の概念分離

raw color（red-500 / blue-500 等）を一律禁止するのではなく、用途で分ける：

| 種別 | 例 | 扱い |
|---|---|---|
| **物の色**（識別） | kazoe-bou の位（pink/yellow/blue）、kuku の行/列、sakusen-board のチーム色、トップページの教科色 | **raw color OK**（むしろ意図的）|
| **ボタンの色** | もんだい・セット・リセット等 | **トークン必須**（brand/accent/warm/danger） |

これで「教科識別の10色は維持しつつ、ボタンは一貫して統一」が両立。

## ふりかえり・気づき

### 良かったこと

1. **段階的移行計画（Phase 0〜6）を最初に設計書に書いた**
   - 各 Phase 完了ごとにユーザー確認を取りながら進めたので、迷子にならなかった
   - 「Phase 1 のサンプル（BtnQuestion）を1つだけ書き換え→確認→残り9つ一気」のパターンが効いた

2. **danger トークンの「変数化」**
   - オーナーの「あとで変えたいかも」という不確実性に対し、CSS 変数のエイリアスで応えた
   - 設計判断の根拠が明確で、将来の意思決定コストを劇的に下げる

3. **「物の色」と「ボタンの色」の概念分離**
   - 一律禁止ではなく用途別ルール → 既存の正当な raw color（kazoe-bou の位識別など）を壊さずに済んだ

### 反省・気をつけたいこと

1. **私が「BtnUndo = brand」を「初期方針」と早合点した**
   - 一つの根拠（共通部品の実装）から全体を推測してしまった
   - オーナーから「実際は okane=グレー、kyoto-ku=オレンジ」と具体例を挙げられて初めて全体像が見えた
   - **教訓**: 設計の「初期方針」を主張する前に、複数の根拠（コード+メモリ+docs）を並べて検証する

2. **kake-hissan2 と kazoe-bou の取り違え**
   - 調査レポートで「kake-hissan2 の位ごとのくりあがり pink/yellow/blue」と書いたが、実は kazoe-bou の話だった
   - grep の path 指定を取り違えた可能性
   - **教訓**: マトリクス系の調査結果は path を含めて引用する

3. **「ブランド」の意味を最初に確認すべきだった**
   - 私は「brand トークン1色」と解釈、オーナーは「全色のトーン統一」と解釈
   - 議論を進めて初めて齟齬に気づいた
   - **教訓**: 抽象語（「ブランド」「統一感」「やわらかい」など）は最初に具体例で擦り合わせる

# 📤 他チャットでも振り返りレポートを作るためのプロンプト

> 他のチャットでもゴリゴリに開発を進めて振り返りができていない件があるので、各チャットに以下のプロンプトを投げて、同様の振り返りレポートを `docs/` に作成してもらう。
> **チャット間で内容の重複がある可能性があるため、重複チェック手順も含める。**

## ⚠️ 利用ルール

- 各チャットには **1 回だけ** 投げる（同じ内容のレポートが二重に作られないように）
- 投げる前に「このチャットには既に振り返りを依頼したか？」を念のため確認する

## プロンプト本文（コピーして使う）

````markdown
このチャットで進めた作業の「振り返りレポート」を `docs/` に Markdown ファイルとして保存してください。
ゴリゴリ開発を進めて振り返る暇がなかったので、後から読めるドキュメントとして残したいです。

## 重複チェック（必ず最初に実行）

1. まず `docs/` 配下を `Glob` で確認し、`report_YYYY-MM-DD_*.md` という形式のファイル一覧を取得してください。
2. このチャットで進めた作業のテーマと **明らかに重複するレポートが既に存在する** 場合（同じ日付・近いテーマ・主要ファイルが重複）は、
   **新規作成をキャンセル**し、「既に `docs/<該当ファイル名>` に振り返りレポートが存在するため、重複を避けて作成を見送りました」と返答してください。
3. 重複がなければ次のステップに進む。

```

- `docs/report_2026-04-26_ふしづくり拡張.md`
````
