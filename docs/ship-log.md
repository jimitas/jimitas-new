## 2026-09-20 — アルゴリズムの「終わった瞬間」に音を鳴らす（段階5の判断）

**コミット：** `87bd05c`

### 背景・目的

アルゴリズムシミュレーターの段階5（仕上げ）で、ひとつだけ決めずに残していたのが
効果音だった。オーナーの判断で「鳴らす」に決定。

### 何を鳴らすか

| 場面 | 音 |
|---|---|
| ソートが終わった | `seikai2`（少し華やか） |
| 探索で見つかった | `seikai1` |
| 探索で見つからなかった | `cancel`（短い） |

見つからなかったときに `alertSound` を使わなかったのは、**これは不正解ではなく
アルゴリズムの正しい答え**だから。警告音にすると「まちがえた」と受け取られる。

**再生中は1ステップごとに鳴らさない。** n=50 で数千ステップあり、
全部鳴らすと音が重なって意味をなさない。

### 技術的なポイント

**「2回続けて鳴る」をどう防いだか。**

探索は `found`（または `notfound`）のうしろに `done` を置いている。
`kind` を素直に見て鳴らすと、**見つけた瞬間と終了で2回鳴る。**

そこで「どこで鳴らすか」を決める `finishCue()` を `_lib/` に純関数として置いた。
探索は found / notfound の瞬間、ソートは done。**合図は必ず1か所に絞られる。**

`_lib/` は React・DOM・`@/lib/se` に触らない約束なので、この関数は
「どの合図か」を返すだけ。音は画面側で鳴らす。
おかげで **鳴る位置を jest で検査できる**（音そのものは機械に聞けないが、
位置だけでも機械に見張らせる）。

### 検証

- `finishCue.test.ts` 13件。**found を見ないように壊すと探索4件が落ちる**ことを確認して戻した
- 実機で `AudioBufferSourceNode.start` を数えた

| 試したこと | 鳴った回数 |
|---|---|
| 選択ソート n=5 を1→30まで | 1回（3.04秒＝seikai2） |
| 二分探索・ある値 | 1回（2.11秒＝seikai1）。その先の `done` では鳴らない |
| 線形探索・ない値 | 1回（0.1秒＝cancel） |
| ミュート中に同じ瞬間を通過 | 0回 |

**RAFはタブが裏だと止まる**ので、再生ボタンでは最後まで進まない。
検証は ← → のコマ送りで行った（この癖は前にも踏んでいる）。

### あわせて直したもの

`page.tsx` の見出しコメントが「現状: 段階1a（選択ソートのみ）」のままだった。
8本入ったあとも誰も直していない、典型的な仕様と実装のズレ。

### 持ち越し

- 説明文とコード例の**文言レビュー**（人の目が要る。自動テストでは担保できない）
- コマ送りで戻ってまた進むと もう一度鳴る。授業で うるさければ

## 2026-09-20 — たしざん1・ひきざん1 の2件を直し、「6本のうち2本だけ穴が空いていた」ことを確かめる

**コミット：** `365dd98`

### 背景・目的

オーナーが実機で見つけた2件を直した。場所は前のセッションで特定済みで、
**片方は設計判断が要る**という状態で引き継がれていた。

### ① 式の入力欄で2桁が見切れる

`PutShiki.tsx`（使うのは `tashizan-1` と `hikizan-1` の2本だけ）。

引き継ぎでは `type="number"` のスピナーが疑われていたが、**実測すると単純な幅不足**だった。

| | 値 |
|---|---|
| 入力欄の内側 `clientWidth` | 51px |
| 中身 `scrollWidth` | 62px |
| 文字に使えた幅 | 41px（幅4vw − パディング10px − 枠3.2px） |
| 2桁の実寸 | 約52px（UD教科書体ボールド 2vw） |

`w-[max(4vw,42px)] px-[5px]` → **`w-[max(5vw,52px)] px-0`** に変更。
`text-center` なので左右パディングは元々不要だった。

**ここが効く**: 幅も文字サイズも vw 依存なので、**比がすべて**になる。
必要なのは `幅 ≥ 1.93 × 文字サイズ + 枠`。`4vw` は文字の 2.0 倍しかなく、
パディングを外しても足りない（4.10 倍必要）。**この比を下げると再発する。**

### ② こたえをみた後に こたえあわせ するとコインがもらえる

`showAnswer()` が答え欄に正解を書き込むだけで、問題を終了させていなかった。

| アプリ | showAnswer の中身 | 判定 |
|---|---|---|
| tokei | `setHasProblem(false)` | もともと安全 |
| amari | `setStep("done")` | もともと安全 |
| number-line | `setIsActive(false)` | もともと安全 |
| kazu | コイン機能なし | 該当なし |
| **tashizan-1 / hikizan-1** | **何もしない** | **穴** |

「A案：こたえあわせは押せるがコインは出さない／B案：こたえあわせを無効化」で
相談したが、**4本がすでに B案だった**ことがそのまま答えになった。
オーナーの判断で B案を採用し、`setHasProblem(false)` を追加。
これで数字ボタン・Enter・こたえあわせの3経路が同時に閉じる。
押せなくなるので、2回押しで答えが消えるトグル分岐は落とした。

**あえてやらなかったこと**: `BtnShowAnswer` に `disabled` を渡していない。
この2本は不正解時に `hasProblem` を1秒だけ false にするため、
渡すと不正解のたびにボタンがグレーに点滅する（他4本にはこの挙動がない）。

これがないと、コインが常に増えない実装に変わっても検査は緑のままになる。

## 2026-09-20 — 持ち越し4件を片づけ、検査の「見ていない場所」を3つ塞ぐ

**コミット：** `f73c828`

### 背景・目的

引き継ぎ書に残っていた「小さい持ち越し」4件を片づけた。
どれも急ぎではなかったが、**着手したら本体の不具合が1件出てきた。**
持ち越しの正体は「まだ検査していない場所」であって、
検査していないところに不具合が残っていた、という順番だった。

### 変更内容

| 持ち越し | やったこと |
|---|---|
| smoke の 600ms 固定待ち | `data-hydrated` 属性を待つ方式に置きかえ |
| `dark-after-question` の未カバー2本 | `tokei` / `suuzu-block` を SETUP つきで追加 |
| 「こたえあわせ」後の状態が未検査 | 二段目の検査を追加し、ラベルの表記ゆれまで拾う |
| `masu-nuri` を `BtnMode` に寄せるか | **見送り継続**（非選択が灰色で見た目が変わるため） |

### 見つかった不具合（本体の修正）

**数図ブロックの上エリアの罫線が、ダークで背景に溶けていた（1.28:1）。**

`Block.module.css` は上エリアと木箱の中に**同じ黒い罫線**を引いていた。
ところが地の明るさが両者で違う。

- 上エリア … 地はページの背景そのもの（ライト＝白／ダーク＝紺）
- 木箱の中 … 地は白を55%かぶせたクリーム色で、**テーマによらず明るい**

黒固定だと上エリアだけがダークで消える。
かといって両方 `currentColor` にすると、今度は木箱の中が
「明るいクリーム地に白い線」になって逆に消える（実際に一度そうしてしまい、実機で気づいた）。
**地の明るさが変わる面だけ線を文字色に追従させる**のが正解で、CSS を2つに分けた。

### 技術的なポイント

**1. 固定時間の待ちをやめた**

`NoContextMenu` の effect で `<html data-hydrated="1">` を付け、smoke はそれを待つ。
effect はハイドレーション後に走るので、**この属性が付いた時点で
ハイドレーション不整合のエラーは出そろっている**と言い切れる。
`kyoto-ku` にわざと不整合を入れて赤くなること、戻すと緑になることを確認した。

**2. 検査の「届いていなさ」は、緑の中に隠れる**

二段目の検査を `/こたえあわせ|たしかめ/` で書いたが、**筆算5本が1つも引っかからなかった。**
わり算・かけ算2 は漢字の「答え合わせ」、たし算・ひき算・かけ算1 は
合わせるボタン自体が無く「こたえ」だった。
**2026-09-12 のダーク罫線バグが出たのはその筆算**で、
いちばん見たいアプリが静かに検査の外にいた。

気づけたのは、わざと `.toBe(-1)` にして**何本が赤くなるかを数えた**から。
全部緑のままでは「届いていない」は一生見えない。
表記を広げた結果、二段目に届くアプリは **5本 → 12本** になった。

**3. 「テストが緑」と「直っている」は、CSS では特にずれる**

`.lowerGrid` を `currentColor` にした失敗は、ダーク検査では**緑のまま**だった。
検査の `effectiveBg` は半透明を合成するので、白55%を重ねた木箱の地は
「明るい」とも「暗い」とも判定されない中間色になり、判定の対象から外れる。
最後に実機のスクリーンショットを見て気づいた。

## 2026-09-20 — 挿入ソートを共通テスト方式（取り出してずらす）に作り直す

**コミット：** `b132bde`

### 背景・目的

段階1b で入れた挿入ソートは「となりと入れかえながら左へ歩かせる」書き方にしていた。
画面上で値が2つに見える状態を作りたくなかったため。

**現在の教科書には挿入ソートが載っていないので、共通テストの書き方に合わせたい**
という判断をもらったので作り直した。

### 変更内容

| | 変更前 | 変更後 |
|---|---|---|
| 書き方 | となりと入れかえながら左へ歩く | tmp に取り出す → ずらす → さしこむ |
| tmp の役割 | 入れかえのための一時変数 | **手に持っているカード** |

```
kazu = 要素数(Data)
i を 1 から kazu-1 まで 1 ずつ増やしながら繰り返す:
｜ tmp = Data[i]
｜ j = i-1
｜ j >= 0 and Data[j] > tmp の間繰り返す:
｜ ｜ Data[j+1] = Data[j]
｜ ⎿ j = j - 1
⎿ Data[j+1] = tmp
表示する(Data)
```

回数の性質は変わっていない。ならんだ入力で くらべる n−1 回・ずらす 0 回、
逆順で どちらも n(n−1)/2 回。

### 技術的なポイント

**この方式の落とし穴**
取り出してからさしこむまでのあいだ、配列にはまだ古い値が残っていて
**同じ数字が2つ並んで見える**。そのままだと「値が増えた」と誤解される。

そこで「取り出した値（held）」と「あいた場所（gap）」を Recorder が持ち、画面では

- 取り出した値 … 穴の真上に浮かぶオレンジの `tmp` 札
- あいた場所 … 点線のわく。**値ラベルも空欄にする**

として描く。穴が左へ動くと札も一緒に動く。
実機で見たとき、最初は値ラベルだけ古い値が残っていたので直した。

`tmp` の矢印は出していない。札そのものが `tmp` なので二重になるうえ、
取り出したステップだけ凡例が増えて目が散るため
（矢印の凡例を固定表示にしたのと同じ理由）。

**配列スナップショットの更新条件を変えた**
これまでは「どの kind が配列を変えるか」の表（`isSwapKind`）で判断していたが、
**中身が実際に変わったか**を見るように変えた。

新しい操作（`take` / `place`）を足したときに表の更新を忘れると、
画面が1つ前の配列を出しつづけて**無言で嘘をつく**。
n は 50 までなので、毎ステップ中身を比べるコストは無視できる。
実際に更新しないよう壊してみると 130 件落ちた。

**Recorder に4つ追加**
`takeOut` / `greaterThanHeld` / `shiftRight` / `putDown`。
手の状態は `push` のたびに全ステップへ自動で付くので、生成器が付け忘れられない。

**数え方**
「ずらした回数」は `Data[j+1] = Data[j]` が動いた回数だけ。
取り出しとさしこみは必ず n−1 回ずつ起きるので数えても情報にならない。
カウンタのラベルはアルゴリズムごとに変えられるようにした
（入れかえた回数／ずらした回数。探索は常に0なので表示自体をやめた）。

### テスト

614件。

**多重集合不変を「逃げずに」全ステップで要求できるようにした。**
取り出し中は「穴に手の中の値を戻した配列」を見る。
これなら「取り出している最中は検査しない」と例外を作らずに済む。

```ts
export function effectiveArray(s: Step): number[] {
  const a = [...s.array]
  if (s.held !== undefined && s.gap !== undefined) a[s.gap] = s.held
  return a
}
```

手の操作そのものも固定した。

- 取り出しとさしこみが n−1 回ずつ、必ず対になる
- 取り出したあと、さしこむまではずっと `held` がある
- 穴が動くのは ずらしたときだけ。1回に1マスずつ左へ
- ずらすのは「穴の左どなりの値を穴へ」の1マスだけ

| 壊し方 | 落ちたテスト |

### 技術的なポイント

**ステップ列モデル**
アルゴリズムを実行しながら描画するのではなく、実行の記録を `Step[]` として先に全部作り、
画面は添字を進めるだけにした。再生・一時停止・コマ送り・速度変更がすべて添字の操作になり、
アルゴリズム側に再生制御が漏れない。n=50 で約1,550ステップ、構造共有込みで数百KB。

**Recorder パターン（今回いちばん効いた設計）**
アルゴリズム本体は `Recorder` に対してだけ書く。配列をくらべる手段が `rec.lessThan` しか
無いので、**「比較したのに数え忘れる」が原理的に起きない**。カウントは `StepKind` から自動集計する。

実装は2つ（`StepRecorder` / `CountRecorder`）だが**アルゴリズム本体は1本**なので、
段階3の計算量グラフとアニメーションのカウンタが食いちがうことがない。
さらに「2つが常に一致すること」を単体テストで固定した。

**コード行ハイライトは行番号を持たない**
行番号の対応表を別に持つと、コードを1行足しただけで全部ずれ、しかも無言で間違った行が光る。
かわりにコード例の各行に意味ラベル（`CodeTag`）を直接付け、ステップの `codeTag` と
一致した行を光らせる。これで「言語ごとに行数がちがう」問題も消えた
（Python の1行と疑似言語の3行が、同じ `swap` タグでまとめて光る）。

**テスト（494件）**
不変条件（昇順で終わる／多重集合不変／カウンタ整合／添字が範囲内）に加えて、
アルゴリズムごとの性質を等式で固定した。選択は比較 n(n−1)/2・交換ちょうど n−1、
バブルは早期終了でならんだ入力なら n−1、挿入も同じく n−1、など。

コード例と実装の乖離は**双方向のタグ網羅テスト**で検出する。
疑似言語の罫線（`｜` U+FF5C / `⎿` U+23BF）と、ブロックの深さのつじつまも機械的に検査する。
半角 `|` や `└` に置きかわっても人の目では気づきにくいため。

**安全機構が実際に働くことを14通り確認した**（確認後に復元）。

| 壊し方 | 落ちたテスト |
|---|---|
| 内側ループを `j < n` → `j <= n` | 添字が範囲外 |
| swap を片側代入だけに | 多重集合が壊れる |
| 途中の mark を忘れる | 最後に全部確定していない |
| 集計から `shift` を外す | カウンタ整合 |
| 「入れかえ不要なら飛ばす」最適化 | 交換回数が n−1 でなくなる |
| コード例から1行消す／タグの綴りを変える | タグ網羅（双方向） |
| 疑似言語の罫線を半角に | 記法チェック |
| バブルの早期終了を消す | ならんだ入力は1巡で終わる |
| バブルを飛び越して比較 | くらべるのは必ずとなりどうし |
| 挿入の while から比較を外す | ならんだ入力は n−1 回 |
| 交換ソートを選択ソート化 | 逆順では選択より入れかえが多い |

対象は「もんだい」ボタンを持つ**14アプリ**（47件はスキップ）。
筆算5本はすべて入っている。全アプリに一律でクリックを入れると
誤検出と実行時間が両方増えるため、押す意味のあるアプリだけにした。

### 技術的なポイント：罫線には文字と別の原理が要る

最初は文字と同じ判定（コントラストが低ければ拾う）を使った。**4件の誤検出が出た。**

`header` / `footer` / `nav` の区切り線は**意図的に控えめ**で、コントラストは低い。
しかも全ページに出るので **61アプリ×3件**のノイズになり、本物が埋もれる。

閾値をいじるのではなく、原理を変えた。**効くのは明るさの向き。**

> 暗い背景の上では、線は**背景より明るい**ことで見える。
> 背景より暗い線は原理的に見えない。明るい背景の上ではその逆。

- わり算の罫線: `black`（輝度 0）が `rgb(17,24,39)`（輝度 0.0087）の上 → **背景より暗い** → 検出
- 意図的な区切り線: `gray-700`（0.051）が `gray-800`（0.025）の上 → **背景より明るい** → 除外

これで誤検出4件が消え、**本物1件だけ**が残った。

### 技術的なポイント：検出が静かに1件消えた

途中、`katakana` の 🍌 が 1.02:1 で誤検出された。
カラー絵文字はフォント自身が色を持ち、CSS の `color` を無視して描画されるため、
白文字扱いでも実際には見える。そこで「絵文字だけの要素は検査しない」規則を足した。

その規則に `\p{Emoji_Component}` を使ったところ、**11件検出が10件に減った。**

原因は **半角数字 0-9 が `Emoji_Component` に含まれる**こと
（1️⃣ のようなキーキャップ絵文字の部品として Unicode で定義されている）。
そのため `wari-hissan` の数字パレットが「絵文字だけ」と誤判定され、
**本物の検出が黙って消えた**。

**判定を変えるたびに本物のバグで再検証していなければ、気づかないまま入っていた。**
`Extended_Pictographic` と肌色修飾子・異体字セレクタだけを除く形に直して11件に戻した。

**コミット：** `f47e39a`

### 背景・目的

### 原因


このプロジェクトが最も嫌う形（[[開発文化 2]]「テストが通っている ≠ テストが機能している」）

`networkidle` に変えても足りなかった。実測すると：

| | 時刻 |
|---|---|
| domcontentloaded | 131〜214ms |
| networkidle | 1053〜1240ms |
| **ハイドレーションエラー到達** | **559〜1151ms** |

**エラー到達が networkidle の前後にばらつく。** 実際 `networkidle` だけにした状態で

## 2026-09-12 — ダークモードで白地に白文字になっていた17アプリを修正

**コミット：** `451ab49`（トークン） / `fb98da7`（アプリ修正＋テスト）

### 背景・目的

オーナーからの報告がきっかけ。

> 一部のページでダークモードになると背景が白で文字も白くなるので見にくくなるページが
> 存在するかもと思いました。漢字テストはその一つですが調査できていません。
> スクリーンショットを貼ろうとしたのですが、意外にもすべてうまく表示されていたのでやめました。

**見立ては当たっていた。** 目視で見つけられなかったのは、直前に見出し（h1）だけを
修正していたため、ぱっと見の印象が改善していたから。中身は壊れたままだった。

全62アプリを機械的に走査した結果、**17アプリ**が該当。

### 原因は2つあった

**① 明るい面の中で文字色が指定されていない（本命）**

`bg-white` などの明るい面に `dark:` が付いておらず、中の文字が色指定を持たないため
ダークモードの body の文字色（`#f3f4f6`）を継承して白地に白文字になる。
漢字テストの印刷プレビューはコントラスト **1.1:1** で、タイトルも氏名欄も問題番号も
実質見えない状態だった。

**直し方は「背景を暗くする」ではなく「文字色を固定する」。**
紙・ノート・盤面はダークモードでも白いのが正しいため。ここを機械的に
`dark:bg-gray-800` で潰すと印刷プレビューとして意味をなさなくなる。

**② 存在しないカラートークンが9種類使われていた（根が深い）**

```
accent-900 / warm-700,800,900,950 / rose-300,700,800,900
```

`globals.css` の `@theme` に定義がない。**Tailwind v4 では未定義濃度のクラスは
CSS がまったく生成されず、エラーにもならずに何も起きない。**
書いた側は色が付いているつもりでいるため、気づくのが非常に遅れる。

実害の例。`oto-dashiyo` の音階ボタンは `bg-warm-100 dark:bg-warm-900` と書いてあるのに、
`warm-900` が存在しないのでダークでも背景が明るいまま。文字も明るいので 1.18:1。
`dark:` が付いていない6件（`text-warm-700` など）は**ライトモードでも効いていなかった**。

このプロジェクトが最も嫌う「静かに壊れる」パターンそのもの。

### 変更内容

土台（トークン）とアプリ修正を別コミットに分けた。「トークンが生き返ったことによる変化」と
「明示的に直した変化」が混ざると、問題が出たとき切り分けられないため。

| `recorder` | 暗い地に暗い文字。`dark:text-gray-200/300` を追加 |
| `katakana` / `romaji` | プレースホルダ「─」が 1.47:1。ライトでも薄すぎたので gray-500 に |

トークン追加だけで17→13、残りを直して13→0。

## 2026-06-14 — Vercelリクエスト削減（prefetch無効化＋印刷ページ静的化）

**コミット：** `7691436`

### 背景・目的
Vercel の Edge Requests が月 2,015,611 件に達し、無料枠 1M/月 を大きく超過していた。一方 Google Search Console のクリック数は 1 日約 150 回で、実クリック数とリクエスト数が **400 倍以上乖離**していた。オーナーの仮説（じみぷりの「作成」ボタン押下／旧WordPress URLの404クロール）を検証したところ、いずれも主因ではなく、Next.js の構造的な 2 点が原因と判明したため是正した。

### 変更内容
| 対策 | 内容 |
|---|---|
| **prefetch無効化（最大の削減）** | `AppCard`（トップ約61カード）・じみぷりメニュー（39リンク）・`Header`（4リンク）の全 `<Link>` に `prefetch={false}` を付与 |
| **じみぷり印刷ページの静的化** | `/jimipri/[printId]` をサーバー/クライアント分割。`generateStaticParams` で全39種をビルド時SSG化、`dynamicParams=false` で未知IDは静的404 |

- 仮説①②はいずれも主因ではないと確定（「作成」ボタンは client state 更新のみでネットワーク無し／アクセス元 DOCOMO・KDDI は実ユーザーで bot 主体ではない）

### 技術的なポイント
- **なぜ prefetch がリクエストを爆増させるか**: Next.js の `<Link>` はデフォルトでリンクが viewport に入るたび RSC ペイロードを先読みする。Vercel の Edge Requests は「cached and uncached」を**両方計上**するため、キャッシュヒットでも 1 件として積み上がる。リンクが多いトップ／メニューでは 1 閲覧が数十リクエストに膨張していた。
- **静的化の効果**: 旧実装は `"use client"` + `useParams()` で `generateStaticParams` 未定義 → 39ページ全てがオンデマンドのサーバーレンダリング（キャッシュ率0%・Function呼び出し）だった。問題生成はクライアントの純粋関数でサーバーデータ不要なため、ロジックを `PrintClient.tsx`（`printId` を props 受け取り）へ分離し、ページをサーバーコンポーネント化して SSG（CDNキャッシュ配信）に転換。
- 検証: `npm test` 73/73 pass、`npm run build` で `/jimipri/[printId]` が `ƒ (Dynamic)` → `● (SSG)` に変化することを確認。本番効果は Vercel Usage で 1〜3 日かけて計測予定。
