### 技術的なポイント

**ステップ列モデル**
アルゴリズムを実行しながら描画するのではなく、実行の記録を `Step[]` として先に全部作り、
画面は添字を進めるだけにした。再生・一時停止・コマ送り・速度変更がすべて添字の操作になり、
アルゴリズム側に再生制御が漏れない。n=50 で約1,550ステップ、構造共有込みで数百KB。

**Recorder パターン（今回いちばん効いた設計）**
アルゴリズム本体は `Recorder` に対してだけ書く。配列をくらべる手段が `rec.lessThan` しか
無いので、**「比較したのに数え忘れる」が原理的に起きない**。カウントは `StepKind` から自動集計する。

実装は2つ（`StepRecorder` / `CountRecorder`）だが**アルゴリズム本体は1本**なので、
段階3の計算量グラフとアニメーションのカウンタが食いちがうことがない。
さらに「2つが常に一致すること」を単体テストで固定した。

**コード行ハイライトは行番号を持たない**
行番号の対応表を別に持つと、コードを1行足しただけで全部ずれ、しかも無言で間違った行が光る。
かわりにコード例の各行に意味ラベル（`CodeTag`）を直接付け、ステップの `codeTag` と
一致した行を光らせる。これで「言語ごとに行数がちがう」問題も消えた
（Python の1行と疑似言語の3行が、同じ `swap` タグでまとめて光る）。

**テスト（494件）**
不変条件（昇順で終わる／多重集合不変／カウンタ整合／添字が範囲内）に加えて、
アルゴリズムごとの性質を等式で固定した。選択は比較 n(n−1)/2・交換ちょうど n−1、
バブルは早期終了でならんだ入力なら n−1、挿入も同じく n−1、など。

コード例と実装の乖離は**双方向のタグ網羅テスト**で検出する。
疑似言語の罫線（`｜` U+FF5C / `⎿` U+23BF）と、ブロックの深さのつじつまも機械的に検査する。
半角 `|` や `└` に置きかわっても人の目では気づきにくいため。

**安全機構が実際に働くことを14通り確認した**（確認後に復元）。

| 壊し方 | 落ちたテスト |
|---|---|
| 内側ループを `j < n` → `j <= n` | 添字が範囲外 |
| swap を片側代入だけに | 多重集合が壊れる |
| 途中の mark を忘れる | 最後に全部確定していない |
| 集計から `shift` を外す | カウンタ整合 |
| 「入れかえ不要なら飛ばす」最適化 | 交換回数が n−1 でなくなる |
| コード例から1行消す／タグの綴りを変える | タグ網羅（双方向） |
| 疑似言語の罫線を半角に | 記法チェック |
| バブルの早期終了を消す | ならんだ入力は1巡で終わる |
| バブルを飛び越して比較 | くらべるのは必ずとなりどうし |
| 挿入の while から比較を外す | ならんだ入力は n−1 回 |
| 交換ソートを選択ソート化 | 逆順では選択より入れかえが多い |
| `saisho` を改名して凡例を直し忘れる | 矢印とコード例の変数名の対応 |

### 決めたこと

- **`_components/` を新設**（このプロジェクト初）。単一ファイルだと段階4時点で1000行を超えるため。
  `_lib/` は React・DOM・音・localStorage に触らない純TS に保ち、jest から直接読めるようにした
- **選択ソートの入れかえは `i === saisho` でも省略しない**。コード例に分岐が無いので、
  省くと画面とコードが食いちがう。おかげで交換回数がちょうど n−1 になる
- **挿入ソートは「となりと入れかえながら左へ歩く」書き方**。教科書に多い「取り出してずらす」方式だと、
  途中で配列の中に同じ値が2つ見えて「値が増えた」と誤解される。くらべる回数は同じ
- **バブルの早期終了はフラグを while 条件に入れる**。共通テスト表記に `break` にあたる書き方が
  示されていないため、公式の二分探索の例と同じやり方にそろえた
- **疑似言語の添字は0始まり**（公式例示の既定。Python / JavaScript ともそろう）

- 凡例の「決まった」→「**ならんだ**」。挿入ソートの緑は確定ではなく「もう並んでいる範囲」のため

### 確認してほしいこと

### 変更内容

対象は「もんだい」ボタンを持つ**14アプリ**（47件はスキップ）。
筆算5本はすべて入っている。全アプリに一律でクリックを入れると
誤検出と実行時間が両方増えるため、押す意味のあるアプリだけにした。

### 技術的なポイント：罫線には文字と別の原理が要る

最初は文字と同じ判定（コントラストが低ければ拾う）を使った。**4件の誤検出が出た。**

`header` / `footer` / `nav` の区切り線は**意図的に控えめ**で、コントラストは低い。
しかも全ページに出るので **61アプリ×3件**のノイズになり、本物が埋もれる。

閾値をいじるのではなく、原理を変えた。**効くのは明るさの向き。**

> 暗い背景の上では、線は**背景より明るい**ことで見える。
> 背景より暗い線は原理的に見えない。明るい背景の上ではその逆。

- わり算の罫線: `black`（輝度 0）が `rgb(17,24,39)`（輝度 0.0087）の上 → **背景より暗い** → 検出
- 意図的な区切り線: `gray-700`（0.051）が `gray-800`（0.025）の上 → **背景より明るい** → 除外

これで誤検出4件が消え、**本物1件だけ**が残った。

### 技術的なポイント：検出が静かに1件消えた

途中、`katakana` の 🍌 が 1.02:1 で誤検出された。
カラー絵文字はフォント自身が色を持ち、CSS の `color` を無視して描画されるため、
白文字扱いでも実際には見える。そこで「絵文字だけの要素は検査しない」規則を足した。

その規則に `\p{Emoji_Component}` を使ったところ、**11件検出が10件に減った。**

原因は **半角数字 0-9 が `Emoji_Component` に含まれる**こと
（1️⃣ のようなキーキャップ絵文字の部品として Unicode で定義されている）。
そのため `wari-hissan` の数字パレットが「絵文字だけ」と誤判定され、
**本物の検出が黙って消えた**。

**判定を変えるたびに本物のバグで再検証していなければ、気づかないまま入っていた。**
`Extended_Pictographic` と肌色修飾子・異体字セレクタだけを除く形に直して11件に戻した。

### 検証

| 戻した修正 | 期待 | 結果 |
|---|---|---|
| `b5fb490`（わり算の罫線） | wari-hissan が落ちる | **1.18:1 で失敗**。戻すと緑 |
| `fb98da7`（11アプリの文字色） | 11件落ちる | **11件失敗**。切り出し前と同じ顔ぶれ |

### 背景・目的

18アプリの見た目を移行前後で比べる際、「**コードを変えずに2回撮って差分ゼロ**」を
先に確認したところ、nanbanme だけが毎回違う結果を返した。
ノイズとして避けて段階2は進めたが、原因を追うと Next.js の
開発オーバーレイに「1 Issue」が出ていた（amari は「N」だけでクリーン）。

コンソールを読むと確定した。

```
[error] A tree hydrated but some attributes of the server rendered HTML
        didn't match the client properties. ...
        Variable input such as Date.now() or Math.random()
```

### 原因

```ts
const [order, setOrder] = useState<number[]>(() => shuffled([0..9]))
```

**初期stateの計算は SSR でもサーバー側で走る。** サーバーが引いた乱数と
クライアントが引いた乱数は当然違うので、別の並びを描いて不整合になる。

照合のためにブラウザ側で `Math.random` を差し替えても直らなかったのは、
**サーバー側の乱数までは止められない**ため。

### 変更内容

| 対象 | 内容 |
|---|---|
| `nanbanme/page.tsx` | 初期の並びを固定（`INITIAL_ORDER`）。並び替えは「シャッフル」ボタンのときだけ |
| `tests/smoke.spec.ts` | ハイドレーション完了を待ってから `console.error` を判定するよう修正 |

初期の並びを固定するか・毎回ランダムを維持する（SSRは固定＋マウント後に1回シャッフル）かは
**見える挙動が変わる**ため、オーナーに確認して「固定」を選んだ。
シャッフルボタンは問題ボタンの隣にあり、子ども自身が押せる。

### 技術的なポイント：テストは console.error を見ていたのに、死んでいた

**smoke テストには最初から `console.error` の検査があった。それでも191件グリーンだった。**

原因は `page.goto(..., { waitUntil: "domcontentloaded" })` で判定していたこと。
**React のハイドレーションはそのあとに走る。** エラーが届く前にテストが終わっていた。

このプロジェクトが最も嫌う形（[[開発文化 2]]「テストが通っている ≠ テストが機能している」）
そのもので、**検査を書いた本人も、通っているので機能していると思い込む**。

`networkidle` に変えても足りなかった。実測すると：

| | 時刻 |
|---|---|
| domcontentloaded | 131〜214ms |
| networkidle | 1053〜1240ms |
| **ハイドレーションエラー到達** | **559〜1151ms** |

**エラー到達が networkidle の前後にばらつく。** 実際 `networkidle` だけにした状態で
3回試すと2回落ちて1回通る、という不安定なテストになった。
静止後に 600ms 待って確定させている。

### テストが機能することの確認

- バグを戻して実行 → **5回連続で失敗**
- 修正を戻して実行 → **3回連続で成功**
- 全191件 → 緑（**他のアプリに同種の不整合はなかった**）

実行時間は 2.5分 → 3.6分 に増えた。62アプリ分の待ちが乗るため。

### 副次的な効果

段階2で導入した照合（`npm run layout-compare`）から**既知のノイズの例外が消えた**。
nanbanme も含めて完全に決定的になったので、段階3では36/36の完全一致を要求できる。

### 持ち越し

- `HYDRATION_SETTLE_MS = 600` は実測ベースの値で、**遅い機械では足りなくなりうる**。
  「たまに落ちる」ようになったらまず疑うのはこの値。逆に短くすると検出できなくなる
- `nanbanme` に別の警告が残っている（`/images/monkey.png` の width/height 片側指定）。
  今回の件とは無関係・警告レベルのため触っていない

## 2026-09-12 — ダークモードで白地に白文字になっていた17アプリを修正

**コミット：** `451ab49`（トークン） / `fb98da7`（アプリ修正＋テスト）

### 背景・目的

オーナーからの報告がきっかけ。

> 一部のページでダークモードになると背景が白で文字も白くなるので見にくくなるページが
> 存在するかもと思いました。漢字テストはその一つですが調査できていません。
> スクリーンショットを貼ろうとしたのですが、意外にもすべてうまく表示されていたのでやめました。

**見立ては当たっていた。** 目視で見つけられなかったのは、直前に見出し（h1）だけを
修正していたため、ぱっと見の印象が改善していたから。中身は壊れたままだった。

全62アプリを機械的に走査した結果、**17アプリ**が該当。

### 原因は2つあった

**① 明るい面の中で文字色が指定されていない（本命）**

`bg-white` などの明るい面に `dark:` が付いておらず、中の文字が色指定を持たないため
ダークモードの body の文字色（`#f3f4f6`）を継承して白地に白文字になる。
漢字テストの印刷プレビューはコントラスト **1.1:1** で、タイトルも氏名欄も問題番号も
実質見えない状態だった。

**直し方は「背景を暗くする」ではなく「文字色を固定する」。**
紙・ノート・盤面はダークモードでも白いのが正しいため。ここを機械的に
`dark:bg-gray-800` で潰すと印刷プレビューとして意味をなさなくなる。

**② 存在しないカラートークンが9種類使われていた（根が深い）**

```
accent-900 / warm-700,800,900,950 / rose-300,700,800,900
```

`globals.css` の `@theme` に定義がない。**Tailwind v4 では未定義濃度のクラスは
CSS がまったく生成されず、エラーにもならずに何も起きない。**
書いた側は色が付いているつもりでいるため、気づくのが非常に遅れる。

実害の例。`oto-dashiyo` の音階ボタンは `bg-warm-100 dark:bg-warm-900` と書いてあるのに、
`warm-900` が存在しないのでダークでも背景が明るいまま。文字も明るいので 1.18:1。
`dark:` が付いていない6件（`text-warm-700` など）は**ライトモードでも効いていなかった**。

このプロジェクトが最も嫌う「静かに壊れる」パターンそのもの。

### 変更内容

土台（トークン）とアプリ修正を別コミットに分けた。「トークンが生き返ったことによる変化」と
「明示的に直した変化」が混ざると、問題が出たとき切り分けられないため。

| 対象 | 内容 |
|---|---|
| `globals.css` | 未定義トークン9種を追加（Tailwind 標準ランプに一致）＋印刷面4箇所に文字色固定 |
| 筆算4本 | 表と数字パレットに文字色を固定 |
| `wari-hissan` | **数字パレットのみ**（理由は下記） |
| `suuzu-block` / `kyoto-ku` | 白いカードに文字色を固定 |
| `monty-hall` | `.mh-panel` に `color` を追加（独自の CSS 変数系のため） |
| `recorder` | 暗い地に暗い文字。`dark:text-gray-200/300` を追加 |
| `katakana` / `romaji` | プレースホルダ「─」が 1.47:1。ライトでも薄すぎたので gray-500 に |
| 新規 `tests/dark-readability.spec.ts` | 全アプリ検査の回帰テスト |

トークン追加だけで17→13、残りを直して13→0。

### 技術的なポイント

**測り方を2回間違えて、2回とも修正した。**

1. **半透明背景を合成していなかった** — 最初の集計は18アプリだったが、
   `nihon-todouhuken` は `rgba(200,200,0,0.133)` のカードで、合成すると奥の暗い色と
   混ざって読める。透過を重ね合わせる処理を入れたら消えた（誤検出）
2. **グラデーションを見落としていた** — `monty-hall` のドアは茶色の
   `linear-gradient` だが、**CSS のグラデーションは `background-image` なので
   `backgroundColor` には現れない**。ドアを透明とみなして奥の白いパネルを拾い、
   「白地にクリーム文字」と誤検出していた。背景画像がある要素は
   「判定不能」として見送る形にした

**自分の修正が別の不具合を作り、それをテストが捕まえた。**

`wari-hissan` のテーブルにも他の筆算と同じく文字色を固定したところ、今度は
**暗い地に暗い文字**になった。`rewriteTable()` が
`cell.style.backgroundColor = ""` で React が付けた白背景を消すため、
問題を出したあとのセルは透明（＝ページの地の色）になっていた。
5本のうちこのアプリだけが特殊で、テストがなければ気づかず入れていた。

**dev サーバーが古い CSS を配信して、テストが嘘をつく。**

`globals.css` を編集したあと、起動しっぱなしの dev サーバーは変更を取り込まないことがある。

**白抜きボタンを除外しないと信号が埋もれる。**
低コントラストを無条件に拾うと、配色設計どおりの `bg-danger-400` + 白文字（2.69:1）が
大量に混ざって52アプリが「重大」と出る。「文字も背景も明るい」「文字も背景も暗い」
場合だけに絞ることで、17アプリという正しい信号が出た。

### 検証

Playwright **191件**（スモーク62 + 永続化7 + 見出し61 + 読みやすさ61）全パス /
Jest 83件 / ESLint 0件 / 本番ビルド成功 /

- `katakana` / `romaji` のプレースホルダは**ライトモードの見た目も少し変わっている**

- 背景画像・グラデーションのある要素はテストの対象外。ここは目視に頼る

- **カード内数字**：`text-3xl sm:text-4xl`
- **ドット**：`w-2 h-2 sm:w-3 sm:h-3`、間隔・コンテナ高さもモバイル向けに縮小
- **スタートボタン・説明文**：モバイルで一回り小さいサイズに

### 技術的なポイント
Tailwind のモバイルファースト原則（デフォルト=スマホ小、`sm:` 以上=タブレット）を利用。場エリアのスペーサー（手札行と列を揃えるための透明 div）はモバイルでは不要になるため `hidden sm:block` で非表示に。スマホ用 2×2 グリッドは `grid grid-cols-2 sm:flex` で切り替え、1ファイルの変更のみで対応。
